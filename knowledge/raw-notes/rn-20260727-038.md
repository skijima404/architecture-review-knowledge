# External and Internal Contracts Evolve Through Versioning and Routing

## Note

An External API Contract and the Contracts of its supporting Microservices
normally evolve independently.

An External Contract such as `/api/v1/users` is a promise to Consumers. It may
compose several Internal Contracts:

```text
External Contract v1
  -> Camel Mashup and Routing
     -> Microservice A Contract v2
     -> Microservice B Contract v4
     -> Microservice C Contract v1
```

The Integration Layer maintains Traceability through Version strategy,
Routing, technical Transformation, and Composition. This permits Internal
Services to change while a published External Contract remains compatible.

### Diagnosing Version Growth

An increasing number of External and Internal Version combinations is a
signal, not a root cause.

If Runtime Topology also shows unusually concentrated communication, repeated
data exchange, or coordinated changes, the practitioner suspects an unstable
Microservice Boundary.

If the Topology is not unusually coupled but External Versions continue to
multiply, the practitioner suspects that the API Interfaces were customized
for individual Consumers rather than designed as a reusable API Product. This
is an API Developer Experience and Product-strategy problem.

### API as a Product Economics

The default is a generally useful API Interface.

Every Consumer-specific External Interface multiplies the cost of a Backend
feature:

- interface changes;
- compatibility work;
- testing;
- Documentation;
- Routing;
- support; and
- eventual migration.

A specialized BFF or Mashup is justified when the Business Value exceeds that
continuing cost. Examples offered by the practitioner include communication
optimization as a competitive capability or rapid creation of new Customer
Value through Mashup. These examples are practitioner references, not verified
case studies in this note.

### Publication as a One-way Door

Once an API is published and used, consolidation requires development work in
each Consumer. Provider-side technical reversibility does not remove Consumer
budget, prioritization, testing, and release coordination.

External API publication is therefore often an effective One-way Door. Before
publication, the practitioner would prefer to validate:

- Use Case scope;
- general applicability;
- whether the Interface works as a reusable API Product; and
- the Interface itself with Consumers through UAT.

Roadmap, support, and deprecation practices remain case-specific, especially
across public, partner, and internal APIs.
