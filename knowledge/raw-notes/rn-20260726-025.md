# Some Constraints Challenge the Network Boundary, Not the Protocol

## Note

This note records an interview response to a question in `rn-20260726-024`.

When synchronous behavior appears necessary, the practitioner distinguishes two
different decisions:

1. keep the boundary and change the Integration mechanism; or
2. question whether the responsibilities should be separated by a network
   boundary at all.

When a user interaction requires an immediate result in the same request, an API
may be appropriate instead of Kafka-style asynchronous messaging. This is
typically North-South interaction.

A different problem may exist when compensation cannot be tolerated. This is an
unverified possibility rather than a universal rule. Hard real-time processing
is a representative scenario.

Any Integration boundary introduces network behavior and failure modes. If a
use case cannot tolerate compensation, it may also be highly sensitive to retry,
delay, duplicate execution, and partial failure. In that situation, choosing
between an asynchronous mechanism and a synchronous API may not solve the
problem. The relevant decision may be whether the behavior should be integrated
inside one consistency and deployment boundary.

The practitioner does not apply that conclusion to the whole system from one
exception. All relevant use cases are enumerated, and the analysis identifies
which use cases cannot tolerate the boundary.

The first scope question is whether the strict interaction applies:

- to all communication between the two Microservices; or
- only to one or a small number of Use Cases.

When all communication requires the same strict timing or ordering, the Network
Boundary is strongly questioned.

When the requirement belongs to a specific Use Case, the practitioner
investigates whether the remaining Use Cases can preserve the separation.
Possible solutions are deliberately not standardized. A specialized
Use-Case-specific service or responsibility arrangement is one hypothesis, not
a default.

If no economically rational design can preserve the separation, the Services
are integrated. The comparison considers the Business harm from Timeout and
Performance failure, the implementation and operational Risk of separation,
and the value that separate ownership would retain.

The broader trade-off includes Two-Phase Commit (2PC). When extreme capacity or
autonomy is not part of the architecture value hypothesis, a simpler
transaction approach may remain acceptable. Technical sophistication is not
valuable without a proportional business need.

## Questions

- Which conditions make compensation genuinely unacceptable?
- What evidence shows that a network boundary itself is invalid?
- When does a use-case-specific service isolate an exception, and when does it
  create another responsibility mismatch?
- Under which constraints is 2PC an acceptable trade-off?

asserting an organization-specific implementation.
