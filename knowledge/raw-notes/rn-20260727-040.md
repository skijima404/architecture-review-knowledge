# Event Distribution Balances Authority, Payload, Frequency, and Freshness

## Note

The practitioner prefers East-West Events that state a Business Fact owned by
the Source Domain.

```text
Project Management
  -> Project Created

Repository Provisioning
  -> observes the Event
  -> decides whether and how to provision
```

A Command-shaped message such as `Repository Provisioning Requested` makes the
Source know the downstream capability, direct its execution, and often
understand its parameters. This creates Knowledge and Control coupling and is
avoided by default.

### Data Ownership Before Payload Design

The first question is whether the Source Subdomain has a legitimate use for the
Data.

License, Language, and Repository Template values should not be added to a
Project Management model only because Repository Provisioning needs them. Their
authority may instead belong to Master Data, organization policy, Repository
Provisioning, or a Rule Engine.

If a value already belongs to the Source Domain, the Event Payload depends on
how broadly the Event will be reused.

- A broadly reusable Event is a published Contract and an effective One-way
  Door. It requires careful, general Contract design.
- A highly specific Event can carry only the Source-owned facts required by its
  intended interaction.

Operational metadata such as Event creation time may be useful across Events
for replay and investigation. A universal payload list is not asserted.

### Payload and History Are Case-Specific

Including one or two useful values may avoid an inefficient API call. Large
messages increase Broker, storage, network, and Schema costs, so the
practitioner tries to keep Kafka-style messages small.

Whether to use a Snapshot, current Source API state, Source history, an Event
Log, or an intermediate process-state Service depends on Business Needs and the
Domain Model.

### API, Event, Local Copy, and Hybrid Access

Data authority remains with the Owner, but the access method depends on the
balance between Consumers and the Owner.

- Low-frequency access may be simplest through the Owner API.
- Frequently reused Data may be distributed by Event to minimum Local Copies.
- A strict latest-value requirement may require synchronous access to the
  Owner.
- The same Data may use a Local Copy for ordinary reads and an authoritative
  API for a critical decision.

The practitioner applies this reasoning from Identity Management to
Microservices. User Data is often economical to copy because many Consumers
read it. Other Data may require a current authoritative read. Neither approach
is universal.

## Questions

- Which Source-owned facts make a reusable Event useful without making it
  oversized?
- Which Use Cases require current authoritative state?
- When does Local Copy maintenance cost exceed synchronous API cost?
- How should deleted or invalidated Data be reconciled?
