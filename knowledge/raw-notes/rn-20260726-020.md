# Change Granularity Reveals Distributed Business Value

## Note

This note records an interview response to a question in `rn-20260726-006`.

The practitioner applies this reasoning as a simulation during Microservices
decomposition. A Business Decision or change affecting multiple Bounded
Contexts is not unusual by itself.

High-level initiatives such as a SAFe Epic or Capability can legitimately span
multiple Contexts. A Feature may also span Contexts depending on how it is
defined.

Distribution becomes more suspicious at User Story granularity. A User Story
implemented across multiple Contexts may indicate that one unit of business
value or one system responsibility has been distributed across an unsuitable
boundary.

The story must first be checked for inadequate decomposition. For example,
splitting work into frontend and backend tasks is a technical division and may
not represent independently deliverable value.

The practitioner uses the value expressed by the `so that` portion of a User
Story as a reasoning aid. If that value cannot be meaningfully decomposed, but
realizing it requires the same business decision to be implemented across
multiple locations, the current boundary is considered questionable.

This is a design-time simulation and a reason to investigate the boundary, not
automatic proof that the boundary is invalid.

## Questions

- What forms of User Story distribution remain legitimate across Bounded
  Contexts?
- How should independently valuable slices be distinguished from technical task
  decomposition?
- Does the same reasoning apply when coordination occurs through events rather
  than synchronous calls?
