# Code History Is Evidence of Business Change Pressure

## Note

Code assessment is not only a quality-scoring exercise.

The practitioner reads change history, hotspots, conditionals, duplicated
business rules, exceptions, workarounds, and coordinated module changes as
evidence of where business change has reached the system.

This evidence may reveal accumulated business decisions, missing domain
concepts, boundary misalignment, or future change risk. It must still be
interpreted rather than treated as proof.

Poor code quality does not by itself identify a Core Domain. A strategically
important and frequently changing domain may remain well structured when its
variation has been modeled deliberately. Conversely, poor code can result from
engineering debt without indicating strategic importance.

The relevant question is whether the implementation structure matches the
observed and expected change pressure.
